# SentinelOps Threat Model

STRIDE-style breakdown by component. "Mitigation" describes what's actually
implemented in this codebase today, not aspirational controls. Infrastructure
is now split across 8 CDK stacks (`infrastructure/lib/stacks/`): NetworkStack,
AuthenticationStack, StorageStack, ObservabilityStack, DatabaseStack,
EventProcessingStack, ApiStack, FrontendStack — component rows below
reference whichever stack actually owns the resource.

| Component | Threat (STRIDE) | Mitigation | Residual risk |
|---|---|---|---|
| Cognito / JWT auth boundary (`AuthenticationStack`, `apps/api/Program.cs`, `Auth/CognitoAuthService.cs`) | Spoofing — forged or stolen tokens | JWT validated against Cognito's JWKS; issuer, `token_use == access`, and `client_id` are all checked explicitly (Cognito access tokens don't carry a standard `aud` claim) | Token theft (XSS on a client, leaked token) is not mitigated at this layer — short (1h) access token validity limits the window |
| API Gateway (HTTP API) + VpcLink + private ALB + WAFv2 (`ApiStack`) | Denial of service, common web exploits, SQLi at the edge | AWS-managed Common + SQLi rule groups, a 2000-req/5min per-IP rate-based rule, attached to the API Gateway **stage** (not the ALB — the ALB is private, reachable only via the VpcLink); TLS termination at both the API Gateway custom domain and the ALB, HTTP→HTTPS redirect | WAF is a coarse backstop, not a replacement for the app-level rate limiter in `Program.cs` (see security-assumptions.md); ALB→ECS hop inside the VPC is plaintext HTTP |
| CloudFront + public frontend ALB (`FrontendStack`) | Origin bypass — reaching the ALB directly, skipping CloudFront/WAF | ALB listener rejects (403) any request without a shared-secret `X-Origin-Verify` header that only the CloudFront distribution's origin config is set to send | Security-group ingress on the frontend ALB is still `0.0.0.0/0` at the network layer (CloudFront needs a publicly reachable origin) — the header check is an application-layer control, not a network one; see security-assumptions.md |
| EF Core tenant-isolation boundary (`apps/api/Data/SentinelOpsDbContext.cs`) | Tampering / information disclosure — cross-tenant data access | Every `ITenantOwned` entity (including `AnalyticsEvent`, closed as part of this work) gets `HasQueryFilter(x => x.OrganizationId == currentOrganization.OrganizationId)`; `ICurrentOrganizationAccessor` is populated only after `OrganizationRoleAuthorizationHandler` verifies active membership, so tenant-owned rows are invisible until then. The 8 `IgnoreQueryFilters()` call sites (identity/org bootstrapping, where no org is known yet) are each individually commented with why they're safe | A new query added without going through the DbContext's `DbSet<T>` properties (e.g. a future raw-SQL escape hatch) would bypass the filter — mitigated structurally by the SQL-safety CI check, which blocks `FromSqlRaw`/`ExecuteSqlRaw` entirely |
| API-key ingestion path (`Ingestion/ApiKeyAuthenticationHandler.cs`) | Spoofing, brute force | API key is SHA-256 hashed at rest and compared by hash, not stored/compared in plaintext; ingestion has its own tighter rate-limit policy (50/10s per integration) | No key rotation UI/API observed beyond issuance — operational gap, not a code gap |
| S3 attachment upload path (`StorageStack`, GuardDuty malware protection) | Malicious file upload | Presigned PUT URLs scoped to a specific `StorageKey` prefix (`AttachmentPolicy`); every object PUT is scanned by GuardDuty Malware Protection for S3, which tags scan results consumed by `SentinelOps.Workers.AttachmentScan`; `AttachmentsController`'s download endpoint rejects any attachment whose `ScanStatus` isn't `Clean` (verified at `AttachmentsController.cs:124`); bucket is `BLOCK_ALL` public access, KMS-encrypted, TLS-enforced | None identified for the download path; an attachment stuck in `Pending` (scan not yet complete) is simply undownloadable until it resolves, which is the intended fail-closed behavior |
| SQS / EventBridge worker boundary (`EventProcessingStack`, `ApiStack`'s dashboard workers, `SentinelOps.Workers.*`) | Message replay, duplicate processing | `IdempotencyGuard` + `ProcessedWorkerEvent` table dedupe by event id per worker; DLQs (14-day retention) catch poison messages after 5 receives; custom EventBridge bus isolates SentinelOps traffic from anything else in the account | A worker Lambda with a bug that mis-processes a valid, non-duplicate message isn't caught by idempotency alone — relies on DLQ + alerting on DLQ depth (not configured in this stack) |
| Aurora PostgreSQL / Secrets Manager (`DatabaseStack`) | Credential theft, unencrypted data at rest | `storageEncrypted: true` on the Aurora Serverless v2 cluster with a customer-managed KMS CMK (from `StorageStack`); credentials generated and stored in Secrets Manager (`rds.Credentials.fromGeneratedSecret`), never committed or passed as a plaintext CFN parameter; automatic 30-day rotation via a dedicated `SecretRotation` construct with its own least-privilege security group; `rds.force_ssl=1` requires TLS on the wire | Lambda workers and the ECS API task only re-resolve the secret on cold start / process start (see security-assumptions.md) — a compromised long-warm execution environment retains the old credential until it's recycled. The secret itself uses Secrets Manager's default AWS-owned key rather than the shared customer-managed key, for a structural cross-stack-dependency reason (see security-assumptions.md) |
| IAM / roles per service (all 8 stacks) | Privilege escalation via over-broad roles | Every Lambda function gets CDK's auto-generated, function-scoped execution role (no shared roles); ApiStack's ECS gets two purpose-built roles (`ApiExecutionRole`: ECR pull + logs + DB secret read only; `ApiTaskRole`: S3 read/write on the two app buckets + EventBridge PutEvents only); FrontendStack's ECS gets its own separate execution/task role pair; the GuardDuty malware-protection role is scoped to tagging/read actions on one bucket | None identified — all grants observed use CDK's narrow `grant*` helpers or explicitly scoped `PolicyStatement`s |
| CloudTrail (`ObservabilityStack`) | Repudiation — no record of account-level API activity | Multi-region trail with global service events included, KMS-encrypted, delivered to both S3 (1-year lifecycle) and CloudWatch Logs (1-year retention) | Trail covers AWS API calls, not application-level actions — see `Common/IAuditLogger` for that, a separate and complementary log |
| Route53 / ACM (`ApiStack`, `FrontendStack`) | Domain hijack, TLS downgrade | ACM certificates are DNS-validated against an explicitly imported hosted zone (never `fromLookup`); TLS 1.2+ enforced on every listener/distribution | Hosted zone and domain names are currently `CfnParameter` placeholders (no real domain owned yet) — see security-assumptions.md |

## Application-level vs. AWS-level audit logging

`Common/IAuditLogger` (`AuditLogs` table, `Audit/AuditLogsController`) records
business actions — "user X changed incident Y's status" — scoped per
organization and readable only by Administrators. CloudTrail records AWS API
calls — "someone called `iam:CreateUser`". These are deliberately separate
systems answering different questions; neither substitutes for the other.
